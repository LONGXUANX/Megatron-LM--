函数入口与核心变量初始化

forward_backward_pipelining_with_interleaving input_tensors tensor_shape data_iterator

整个 VPP 调度器的入口是 forward_backward_pipelining_with_interleaving。 它是一个"批导体"：接收用户的 forward_step_func、数据和模型， 将 V×M 个计算事件按三阶段（warmup → 1F1B → cooldown）安排在所有 GPU 上有序执行， 同时通过 P2P 通信在 stage 间传递激活值和梯度。

① forward_step_func：用户提供的前向回调

forward_step_func 来自 pretrain_gpt.py 的 forward_step。 它的职责是：从 data_iterator 取出一个 micro-batch， 调用 model.forward，并返回一个 (output_tensor, loss_func) 元组。

pretrain_gpt.py · forward_step（简化）
def forward_step(data_iterator, model):
    # 1. 从 data_iterator 取 batch（first stage 或 last stage 用到）
    tokens, labels, loss_mask, attention_mask, position_ids = get_batch(data_iterator)
    # get_batch 对 None iterator 返回全零的 dummy tensors（中间 stage 不用）

    # 2. 调用 model.forward，输出是 hidden_states（非 last stage）或 loss（last stage）
    output_tensor = model(input_ids=tokens, position_ids=position_ids, ...)

    # 3. 返回 (output_tensor, loss_func) 二元组
    #    调度器拿到 output_tensor 后发给下游 GPU
    #    loss_func 稍后在 last stage 被 backward 前调用
    return output_tensor, partial(loss_func, labels=labels, loss_mask=loss_mask)

为什么大多数 slot 是 None

中间 chunk 的 input 由 P2P 通信接收——前一个 stage 的 hidden_states 直接注入 TransformerBlock。设为 None 可以在 get_batch 里 做快速判断，避免数据加载操作（数据加载是 CPU 上的重量级操作，不应在无关的 rank 上触发）。

为什么设计成 list-of-list 而不是单一队列

在 warmup 阶段，不同 chunk 的填充速度不同。 例如：chunk 0 可能已有 2 个输入排队（mb=0、mb=1），而 chunk 1 还没有任何输入。 用 list[chunk_id] 可以给每个 chunk 独立维护队列， 避免跨 chunk 的读写干扰。如果用单一队列，就必须同时记录 chunk_id，引入额外复杂度。

offset 变量在 forward_step_helper_preprocess 里的作用实现细节

input_tensors[c] 以 append 方式写入（O(1)）， 以 索引方式读出，而不是 pop(0)（O(n)）。 调度器为每个 chunk 维护一个 input_tensors_offset[c] 计数器：

forward_step_helper_preprocess（逻辑等价代码）
def forward_step_helper_preprocess(chunk_id):
    # input_tensors[chunk_id] 中，offset 指向下一个待消费的 tensor
    input_tensor = input_tensors[chunk_id][input_tensors_offset[chunk_id]]
    input_tensors_offset[chunk_id] += 1
    # 用索引而非 pop(0) 的原因：
    #   pop(0) 对 list 是 O(n)，每次消费都要移动所有后续元素
    #   索引 + counter 是 O(1)，避免 warmup 阶段的性能退化
    return input_tensor

类似地，output_tensors[chunk_id] 也用 output_tensors_offset[c] 控制 backward 时从哪里取 output_tensor。

④ tensor_shape：P2P recv buffer 的预分配依据

在 _communicate() 发起 recv 之前，需要 预先分配一个空 buffer 接收来自相邻 stage 的 tensor。tensor_shape 决定了这个 buffer 的形状：

schedules.py · tensor_shape 计算schedules.py:1100
# 默认形状：[seq_length, micro_batch_size, hidden_size]
tensor_shape = [seq_length, micro_batch_size, config.hidden_size]

# CP 先切：序列维度按 CP size 整除
tensor_shape[0] = tensor_shape[0] // cp_group.size()

# SP 再切：若开启 Sequence Parallelism，再按 TP size 整除
if config.sequence_parallel:
    tensor_shape[0] = tensor_shape[0] // tp_group.size()

# 最终 seq 维度 = seq_len / (CP × TP)，两者可叠加，并不互斥
SP 与 CP 可以同时开启

两者都对 seq_length 做切分，但作用层次不同，可以叠加：

SP（Sequence Parallelism） CP（Context Parallelism）
绑定维度 与 TP 紧耦合 独立并行维度
切分范围 LN、Dropout 等非 attention 层 整条序列（含 attention）
通信原语 all-reduce → reduce-scatter + all-gather（TP 组内） ring P2P（attention 中跨 CP rank 共享 KV）

两者同时开启时，tensor_shape[0] 先被 CP size 整除、再被 TP size 整除， 最终 pipeline P2P recv buffer 的 seq 维度为 seq_len / (CP × TP)，这正是设计预期。 LLaVA 模型代码（llava_model.py:693）也显式处理了 context_parallel and sequence_parallel 同时开启的情形，说明两者可以叠加使用。

requires_grad=True 的必要性

在 _communicate() 内，recv buffer 以 torch.empty(tensor_shape, requires_grad=True, device=...) 分配。这不是可选的：

  • 收到的 tensor 是本 stage 前向计算图的起点， PyTorch autograd 必须能从这里向前追溯梯度。
  • 反向传播时，tensor.grad 会被填入梯度值， 作为 input_tensor_grad 通过 P2P 发回上游 stage。
  • 若设为 requires_grad=False，梯度无法跨 stage 传递， 上游 stage 的参数将永远收不到正确梯度。

virtual_microbatch_id 与主循环三阶段

virtual_microbatch_id (vid) fid / bid get_schedule_table get_model_chunk_id warmup / steady / cooldown

VPP 调度器面临的核心问题是：如何把 V 个 chunk × M 个 micro-batch 的所有计算事件 线性化成一个可遍历的序列？答案是 virtual_microbatch_id（vid）。

virtual_microbatch_id 是什么

vid 是把所有 (chunk_id, microbatch_id) 组合 展平成的线性下标，范围 0 … V×M−1，代表"第几次前向计算事件"。 调度器的所有循环都以 vid 为索引，通过查表获知当前应执行哪个 chunk 的哪个 micro-batch。

get_schedule_table 的构造逻辑

schedule_table 的核心设计思想是按组交替：将 M 个 micro-batch 按 N = pp_size 个一组分批，每批依次分配给 chunk 0、chunk 1、…、chunk V-1。 这样可以确保流水线中的数据依赖关系被满足。

schedules.py · get_schedule_table（逻辑等价代码）schedules.py:820
def get_schedule_table(num_microbatches, num_model_chunks, pp_size):
    """
    返回长度为 V*M 的列表，每个元素是 (microbatch_id, chunk_id)。
    microbatch_group_size (N) = pp_size：每组 N 个 micro-batch，循环分配给各 chunk。
    """
    N = pp_size   # microbatch_group_size_per_vp_stage
    schedule = []
    for mb_group in range(num_microbatches // N):    # 每 N 个 mb 一组
        for chunk in range(num_model_chunks):         # 循环各 chunk
            for mb in range(N):                       # 组内 N 个 mb
                schedule.append((mb_group * N + mb, chunk))
    return schedule
    # 注：实际代码处理 num_microbatches % N != 0 的情况

get_model_chunk_id(vid, forward)

根据 vid 查表得到 chunk_id，但前向和反向使用不同的 chunk_id：

  • 前向（forward=True）：直接返回 schedule_table[vid].chunk_id
  • 反向（forward=False）：返回 V - 1 - schedule_table[vid].chunk_id

反向必须从最后一个 chunk 开始往回传——这是链式法则的要求。 例如当 V=2 时，反向 chunk 0 → 原来的 chunk 1（last chunk）， 反向 chunk 1 → 原来的 chunk 0（first chunk）。

反向 chunk_id 映射（pp=2，V=2，M=4 示例）
# 前向 vid → (chunk, mb)
# vid:   0→(c0,m0)  1→(c0,m1)  2→(c1,m0)  3→(c1,m1)
#        4→(c0,m2)  5→(c0,m3)  6→(c1,m2)  7→(c1,m3)

# 反向 vid → (chunk, mb)  [chunk 翻转为 V-1-chunk]
# vid:   0→(c1,m0)  1→(c1,m1)  2→(c0,m0)  3→(c0,m1)
#        4→(c1,m2)  5→(c1,m3)  6→(c0,m2)  7→(c0,m3)
#
# 反向顺序：先 B(c1,m0), B(c1,m1), B(c0,m0), B(c0,m1)...
# 即先反向 last chunk（c1），再反向 first chunk（c0），符合梯度反传方向。

fid / bid：前向与反向各自的 virtual id

vid 是统一的"计算事件序列号"，调度器在主循环中把它拆成两个具体变量分别驱动前向和反向：

  • fid（forward_k / f_virtual_microbatch_id）：当前步要执行前向的 vid， 通过 get_model_chunk_id(fid, forward=True) 得到正序 chunk_id。
  • bid（backward_k / b_virtual_microbatch_id）：当前步要执行反向的 vid， 通过 get_model_chunk_id(bid, forward=False) 得到翻转后的 chunk_id （V-1-chunk），确保反向从 last chunk 开始向前传梯度。

关键关系：在稳态阶段，bid = fid − num_warmup。 反向始终比前向"落后" num_warmup 步，这正是 warmup 积累的 未消费 activation 缓存数量——稳态每轮 +1 前向缓存、−1 反向消费，保持不变。

input_tensors / output_tensors 队列的 append / index / pop 节奏核心机制

调度器用两组列表（每个 chunk 一个槽）管理前向激活值和梯度的生命周期。 理解何时 append、何时 index 读取、何时 pop 消费， 是看懂整个 VPP 流水线的钥匙。

为什么 leading stage 的逻辑不一样？

函数内部区分了两种 GPU：

  • 非 leading stage（GPU1 in forward）：逻辑极简——
    next_chunk = get_model_chunk_id(vid + 1, forward)
    "我刚做完 vid=X，下一步做 vid=X+1，所以我要 recv 的是 X+1 对应 chunk 的 input，来自 GPU0。"
  • leading stage（GPU0 in forward）：复杂。原因是 GPU0 的 c1 chunk input 不来自 GPU0 自身之前的步骤，而来自 GPU1 的 c0 输出（VPP 循环绕回）， 而 GPU0 比 GPU1 快了 (pp_size-1) 步。

    # 反向时：leading = GPU1（第一个做 backward 的，因为它是 last stage）
    is_leading = is_pp_first_stage() if forward else is_pp_last_stage()

    # 前向时 last_chunk = c1（最后一个 chunk 的激活值不发给任何人，只产生 loss）
    # 反向时 last_chunk = c0（最后一个反向 chunk 不 recv 梯度，只 recv None）
    last_chunk = (num_model_chunks - 1) if forward else 0

    if is_leading:   # ── GPU0 视角（pp=2, V=2） ────────────────────────────────
        # 关键约束：GPU0 比 GPU1 早 (pp_size-1)=1 步
        # 当 GPU0 做完 vid=X 时，GPU1 刚做完 vid = X - 1
        # GPU0 想 recv 的是 GPU1 的 c0 输出（循环绕回给 GPU0 的 c1）
        # 但如果 X < pp_size-1=1，即 X=0，GPU1 还没开始，没有任何输出
        if vid < (pipeline_parallel_size - 1):   # X=0 时
            recv = False

            next_chunk_id = get_model_chunk_id(vid + 1, forward)
        else:
            # GPU1 刚做完的是 vid = X-(pp_size-1) = X-1，对应 chunk：
            next_chunk_id = get_model_chunk_id(vid - (pipeline_parallel_size - 1), forward)
            # 例：vid=1 → GPU1 刚做完 vid=0 (c0,m0) → next_chunk_id = c0
            #     vid=2 → GPU1 刚做完 vid=1 (c0,m1) → next_chunk_id = c0
            #     vid=3 → GPU1 刚做完 vid=2 (c1,m0) → next_chunk_id = c1

        if next_chunk_id == last_chunk:   # vid=3 时 next_chunk_id=c1=last_chunk → recv=False

forward_backward_helper_wrapper 的角色

调度分发器 overlap_p2p_comm pre/post callback forward_step_helper

forward_backward_helper_wrapper 是整个调度器的"调度分发器"。 它根据传入的 f_vid（前向 vid）和 b_vid（反向 vid）的组合， 决定在当前时间槽里做什么：

Warmup 模式：只传 f_vid，b_vid=None

只做前向计算。input 来自 P2P recv（或 data_iterator）， output 存入 output_tensors[chunk_id]，然后 send 给下一 stage。

Steady 模式：同时传 f_vid 和 b_vid → 1F1B

先前向（f_vid），再反向（b_vid）。 overlap 模式下通信与计算并发：前向 send/recv 与反向计算重叠， 反向 send/recv 与下一步前向计算重叠。

Cooldown 模式：只传 b_vid，f_vid=None

只做反向计算。消费 output_tensors[chunk_id] 中 warmup 积累的缓存， grad 发回上一 stage。

overlap_p2p_comm=True 模式下的 4 个回调

当 config.overlap_p2p_comm=True 时，P2P 通信以异步方式提交， 调度器通过 4 个回调函数控制等待和发起时机，实现通信与计算的流水线并发：

回调调用时机做什么
pp_pre_forward(vid) 前向计算开始之前 调用 recv_prev_wait_handle.wait()，等待上一步异步 irecv 完成， 确保 input_tensor 已到位，可以安全读取
pp_post_forward(output_tensor, next_f_vid) 前向计算完成之后 发起异步 isend(output_tensor → next_rank) 把激活值推给下游； 同时发起异步 irecv(buf ← prev_rank) 预取下一个 microbatch 的 input； 把 irecv handle 存入 recv_prev_wait_handles[next_f_vid]
pp_pre_backward(b_vid) 反向计算开始之前 调用 recv_next_wait_handle.wait()，等待梯度 recv 完成， 确保 output_tensor_grad 已到位
pp_post_backward(input_tensor_grad, next_b_vid) 反向计算完成之后 发起异步 isend(input_tensor_grad → prev_rank) 把梯度推给上游； 同时发起异步 irecv(buf ← next_rank) 预取下一个梯度； 把 handle 存入 recv_next_wait_handles[next_b_vid]
"通信与计算并行"的具体含义

isend/irecv 在 CUDA stream 上提交通信 kernel 后立即返回， CPU 不阻塞。GPU 的 CUDA engine 并发执行：通信 kernel（NVLink / IB 数据搬运） 与 matmul kernel（Transformer 计算）在不同 CUDA stream 上同步推进。 直到下一次 pre_forward / pre_backward 的 wait() 才同步到 CPU， 此时通信通常已经完成，实际等待时间趋近于零。

P2P 通信层四层架构

isend / irecv 奇偶交替防死锁 _communicate() P2PCommunicator

P2P 通信被封装成清晰的四层结构，从底层 PyTorch 原语到高层语义 API， 每一层都有明确职责：

Layer 1：PyTorch 原语

最底层是 PyTorch 分布式通信原语：

  • torch.distributed.isend(tensor, dst, group, tag) — 异步发送，立即返回一个 Work handle，不阻塞调用方
  • torch.distributed.irecv(tensor, src, group, tag) — 异步接收，tensor 必须预先分配好，handle.wait() 前数据未到
  • torch.distributed.batch_isend_irecv(p2p_op_list) — 批量提交多个 isend/irecv，减少通信轮次，提升吞吐

所有操作都是非阻塞的：提交后 GPU 通信 kernel 开始执行， CPU 继续运行。调用 handle.wait() 才真正等待完成。

Layer 2：_p2p_ops — 奇偶交替防死锁

当不使用 batch_isend_irecv 时（batch_p2p_comm=False）， 独立的 isend/irecv 存在死锁风险：若所有 GPU 都先阻塞 send， send buffer 满了却没有人 recv，整个系统就会永久挂起。

解决方案：奇偶交替——偶数 rank 先发送后接收， 奇数 rank 先接收后发送。这样总有一方（奇数 rank）先 recv， 打破潜在的循环等待。

def _p2p_ops(tensor_send_next, tensor_send_prev,
             tensor_recv_prev, tensor_recv_next,
             group, ...):
    ops = []
    if group.rank() % 2 == 0:
        # ── 偶数 rank：先 send，再 recv ──────────────────────────
        if tensor_send_next is not None:
            ops.append(dist.P2POp(dist.isend, tensor_send_next,
                                  next_pipeline_rank, group))
        if tensor_recv_prev is not None:
            ops.append(dist.P2POp(dist.irecv, tensor_recv_prev,
                                  prev_pipeline_rank, group))
        if tensor_send_prev is not None:
            ops.append(dist.P2POp(dist.isend, tensor_send_prev,
                                  prev_pipeline_rank, group))
        if tensor_recv_next is not None:
            ops.append(dist.P2POp(dist.irecv, tensor_recv_next,
                                  next_pipeline_rank, group))
    else:
        # ── 奇数 rank：先 recv，再 send ──────────────────────────
        if tensor_recv_prev is not None:
            ops.append(dist.P2POp(dist.irecv, tensor_recv_prev,
                                  prev_pipeline_rank, group))
        if tensor_send_next is not None:
            ops.append(dist.P2POp(dist.isend, tensor_send_next,
                                  next_pipeline_rank, group))
        if tensor_recv_next is not None:
            ops.append(dist.P2POp(dist.irecv, tensor_recv_next,
                                  next_pipeline_rank, group))
        if tensor_send_prev is not None:
            ops.append(dist.P2POp(dist.isend, tensor_send_prev,
                                  prev_pipeline_rank, group))
    return ops
pp=2 时的特殊处理

当 pp_size=2 时，两个 rank 互为邻居（prev=next）。 Megatron 使用两个不同的 communicator group （even_send_odd_recv_group 和 even_recv_odd_send_group） 来允许两个通信方向（forward 和 backward）在不同 group 上并发， 避免 group 内部的顺序约束。UCC backend 例外，需使用同一 communicator。

Layer 3：_communicate() — 核心中间层

_communicate() 是真正的核心：它分配 recv buffer、 组装 ops、控制同步策略。

p2p_communication.py · _communicate()（简化）p2p_communication.py:148
def _communicate(tensor_send_next, tensor_send_prev,
                 recv_prev, recv_next,
                 tensor_shape, config,
                 wait_on_reqs=True, ...):
    # ── Step 1：预分配 recv buffer ──────────────────────────────
    tensor_recv_prev = tensor_recv_next = None
    if recv_prev:
        tensor_recv_prev = torch.empty(
            tensor_shape,
            requires_grad=True,        # ← 反向传播从这里起始，必须为 True
            device=torch.cuda.current_device(),
            dtype=config.params_dtype,
        )
    if recv_next:
        tensor_recv_next = torch.empty(tensor_shape, requires_grad=True, ...)

    # ── Step 2：构建 ops 列表（奇偶交替） ───────────────────────
    if config.use_ring_exchange_p2p:
        # ring_exchange 实现（同时和前后邻居交换）
        reqs = _ring_exchange_p2p(...)
    elif config.batch_p2p_comm:
        ops = _p2p_ops(tensor_send_next, tensor_send_prev,
                       tensor_recv_prev, tensor_recv_next, ...)
        reqs = dist.batch_isend_irecv(ops)  # 批量提交
    else:
        reqs = _p2p_ops_non_batch(...)      # 逐个提交

    # ── Step 3：同步控制 ─────────────────────────────────────────
    if wait_on_reqs:
        for req in reqs:
            req.wait()                      # 阻塞，等所有通信完成
        return tensor_recv_prev, tensor_recv_next, None
    else:
        # overlap 模式：不等待，把 reqs 列表返回给调用方
        # 调用方在下一次 pre_forward/pre_backward 时再 wait
        return tensor_recv_prev, tensor_recv_next, reqs
wait_on_reqs=False 时的 reqs 是什么

返回的 reqs 是 List[torch.distributed.Work]， 每个元素对应一个 isend 或 irecv 操作的句柄。 调用方（通常是 pp_post_forward / pp_post_backward）把它存进 recv_prev_wait_handles[next_vid]，在下一次 pp_pre_forward(next_vid) 时调用 handle.wait()。这个异步 handle 机制是实现通信-计算 overlap 的关键。

VPP 中 prev_rank / next_rank 的特殊含义重要

在普通 PP 中，prev_rank = pp_rank - 1，next_rank = pp_rank + 1。 但 VPP 的流水线是循环的：数据经过 chunk 0 的所有 stage 后， 需要从 last stage 绕回 first stage 才能进入 chunk 1。

因此对于 pp=2（只有 GPU0 和 GPU1）：

  • GPU0：prev_rank = GPU1（循环前驱），next_rank = GPU1
  • GPU1：prev_rank = GPU0，next_rank = GPU0（循环后继）

这意味着 GPU1 在 chunk 0 完成 forward 后，通过 send_next → GPU0 把激活值送给 GPU0 的 chunk 1 forward，这正是 VPP 交错调度的核心 P2P 路径。

def send_forward(self, output_tensors, is_last_stage):
    """Send tensor to next rank in pipeline (forward send)."""

                recv_next=False,

Steady State（1F1B）阶段

1F1B overlap_p2p_comm 通信计算并行 CUDA stream

Steady state 是整个调度器效率最高的阶段：每个时间槽同时完成一次前向和一次反向， GPU 始终处于忙碌状态。以 overlap_p2p_comm=True 模式为例， 一个稳态步骤（steady step）的完整时序如下：

"通信与计算并行"的具体含义

CUDA 有独立的 compute stream 和 communication stream：

  • isend/irecv 提交后，通信 kernel 在独立的 CUDA stream 上执行， 不阻塞 compute stream 上的 matmul。
  • CPU 在提交 isend/irecv 后立刻推进到下一步计算， CPU 也不阻塞。
  • 下一步的 pre_forward.wait() 通常在通信已经完成的情况下立刻返回， 实际等待时间趋近于零（通信时间已被计算时间掩盖）。
  • 当计算时间 ≥ 通信时间时，通信开销被完全隐藏， GPU 利用率达到最大。

Cooldown 阶段

纯反向 排空积压 grad send

Cooldown 阶段是 warmup 的镜像：warmup 积累了多少个前向（warmup 步）， cooldown 就需要消化多少个纯反向。此阶段没有任何新的前向计算， 只是把 output_tensors 中剩余的 warmup 缓存全部做完反向， 并把梯度通过 P2P 回传给上游 stage。

GPU0 Cooldown 步骤（b_vid=4-7，共 4 步）
# Cooldown 只调用 backward_step_helper，无 forward_step_helper
for b_vid in range(steady_steps, total_backward_steps):
    # b_vid=4 → B(c1,m2)；b_vid=5 → B(c1,m3)
    # b_vid=6 → B(c0,m2)；b_vid=7 → B(c0,m3)

    pp_pre_backward()                   # wait for grad recv handle
    backward_step_helper(b_vid)         # autograd backward，消费 output_tensors

    if b_vid < total_backward_steps - 1:
        pp_post_backward(input_tensor_grad)
        # send 梯度给上游 + recv 下一个梯度（非最后一步）
    else:
        p2p_comm.send_backward(input_tensor_grad)
        # 最后一步：只 send，不再 recv
Cooldown 与 Steady Backward 的区别
  • Steady backward：做完 backward 后，在 pp_post_backward 中同时 send 梯度并 recv 下一个梯度，也可能 recv 下一步 forward 的 input （send_backward_recv_forward）。
  • Cooldown backward：不再有 forward，pp_post_backward 只 send 梯度 + recv 下一个梯度（send_backward_recv_backward）。
  • 最后一个 cooldown 步骤只做 send_backward，不再 recv。

全景图关键结论
  • GPU1 比 GPU0 早 2 步进入 steady（warmup=2 vs 4）， 因此 GPU1 的 steady 持续 6 对、cooldown 只有 2 步。总计算事件数相同（各 16 个）。
  • slot 0 时 GPU1 有一个 bubble（等 GPU0 完成第一个 F(c0,m0)）， 这是 VPP 调度不可避免的启动开销，但仅 1 个 slot。
  • steady state 期间两个 GPU 几乎完全满负荷， 每个时间槽都有 F 或 B 在计算，P2P 通信在 overlap 模式下被完全隐藏。
  • output_tensors 的峰值大小 = warmup 步数（GPU0=4，GPU1=2）， 这与标准 1F1B 相比增大了（VPP 代价），但 bubble 率从 p−1m 降至 p−1m⋅v。
